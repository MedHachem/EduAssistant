# Knowledge Embeddings — Design Document

Status: **proposal, not implemented**. No embedding code exists yet. This
document and `embedding_manifest.schema.json` are the full deliverable for
this design phase (Phase 11). Nothing here modifies chunks, relations,
enrichment, normalized knowledge, figures, associations, or the Human
Review system. No Vector DB, semantic search, RAG, or LLM/API call is
implemented or required by this design.

## 1. Real Chapter 1 chunk data, inspected directly

`data/output/math-4eme-tome1-ch01/chunks/knowledge_chunks.json`, measured
directly (not assumed):

- **102 chunks** total: 101 `content_role: "statement"`, 1 `"correction"`.
- **Chunk types by item**: exercise 40, activity 38, theorem 19, property 3,
  definition 1, remark 1 (by first `item_types` entry). 3 chunks have
  `part_index` set (one item split into parts); 1 chunk has 2
  `source_item_ids` (the one confirmed merge).
- **Text length** (`len(chunk["text"])`): min 53, p25 196, **median 280**,
  p75 408, p90 595, **max 3022** (the correction chunk), mean 357. Every
  chunk is small by any embedding model's standard (a 512-token model
  context comfortably fits even the largest chunk; the median chunk is
  roughly 60-80 tokens).
- **Mathematical notation is the dominant characteristic of this corpus**:
  **97/102 chunks (95%) contain at least one `$...$` span**, and math
  delimiters account for **46.9% of all characters** across every chunk's
  `text`. Mean 11.3 LaTeX backslash-commands per chunk (max 129, in the
  correction chunk). This is the single most important fact shaping every
  recommendation below — this is not "French text with occasional
  formulas", it is French/LaTeX genuinely interleaved at near parity.
- **Language**: French prose + LaTeX. Non-ASCII (accented French letters)
  are only 1.38% of characters — the bulk of "special" content is LaTeX
  syntax (`\`, `{`, `}`, `$`, `^`, `_`), not accented text.
- **Metadata available on every chunk** (schema fields, all populated —
  0/102 chunks have empty `topics` or `concepts`): `chunk_id`, `chapter_id`,
  `order`, `source_item_ids`, `item_types`, `section_id`/`section_title`,
  `subsection_id`/`subsection_title` (53/102 chunks have a real
  subsection), `pdf_pages`, `topics`, `concepts`, `has_uncertain_content`,
  `content_role`, `part_index`/`part_count`, `figure_refs` (19/102 chunks
  have at least one), `related_chunk_ids` (90/102 chunks), `generation_methods`,
  `review_status`. **`title`/`display_label`/`exercise_type`/
  `reasoning_types` are NOT chunk fields** — they live one layer up, on the
  normalized item or the enrichment record, and are deliberately NOT
  re-joined into this design (§2).
- **Stable identifiers**: `chunk_id` is already deterministic and
  content-derived (`knowledge_chunking.md` §10) — reused verbatim, never
  regenerated by this phase.
- **Provenance**: `source_item_ids` + `pdf_pages` + `chapter_id` are
  already carried on every chunk — this phase adds no new provenance
  concept, it only needs to preserve what is already there (§4, §6).

**Which field should be embedded?** Not simply `chunk["text"]` verbatim —
see §2 for why, and the concrete example.

## 2. Embedding input strategy

**A. Raw `text` only** — simplest, but throws away the section/subsection/
concept context that already exists on every chunk for free. Concretely
harmful on the corpus's SHORTEST chunks: `math-4eme-tome1-ch01-prop-003`'s
entire `text` is *"La composée de deux fonctions continues est continue."*
(53 characters). Embedded alone, a retrieval query like *"théorème sur la
composition de fonctions continues"* has to rely purely on lexical overlap
with this one sentence — there is no signal that this is a **property**, in
section **"Continuité et limite d'une fonction composée"**, about concept
**"fonction composée"**. All of that is already sitting on the chunk,
unused.

**B. `text` + selected metadata** — recommended, with a specific, narrow
selection (not everything available): `section_title`, `subsection_title`
(when present), `item_types`, and `concepts`. Deliberately **excludes**
`topics` (already redundant with section/subsection title — checked
directly: for every chunk, `topics` is the same set of strings as
`section_title`/`subsection_title`, just also present as a flat list),
`figure_refs`/`related_chunk_ids` (not natural-language content, would
inject IDs into the text stream), and `pdf_pages`/`has_uncertain_content`
(pure provenance/quality flags, not semantic content — these belong in
filter metadata, §10, not the embedded text). `exercise_type`/
`reasoning_types` are **not available on the chunk at all** (§1) — pulling
them in would mean joining `enrichment.json` back in, adding a second
upstream dependency this phase does not otherwise need; left out for now,
noted as a possible future enrichment of this design, not implemented.

**C. A dedicated, deterministic embedding-input template** — this is
what "B" becomes once specified precisely enough to implement:

```
[Chapitre : Continuité et limites]
[Section : Continuité et limite d'une fonction composée]
[Type : property]
[Concepts : fonction composée]

La composée de deux fonctions continues est continue.
```

Built by a pure function `build_embedding_input(chunk, chapter_title) ->
str` — a fixed template, fixed field order, one bracketed line per
populated field (an empty/absent field, e.g. no `subsection_title`,
contributes no line at all — never a blank placeholder), a blank line,
then `chunk["text"]` **byte-for-byte unmodified**. This is Option C
precisely because it is a **derived artifact**, computed fresh from the
chunk every time, never stored back onto the chunk and never treated as a
replacement for `text` — the chunk file itself is never touched (per the
task's boundary).

**Why this matters concretely, using real numbers**: 90/102 chunks are
short enough (under ~600 characters) that a few lines of section/type/
concept context measurably changes what fraction of the embedded input is
"framing" vs. "content" — for the 53-character `prop-003` example above,
the template roughly **doubles** the effective input while adding zero
invented words (every token in the template is copied from an existing
chunk field).

### Handling French + LaTeX specifically

- **Never strip, simplify, or "flatten" LaTeX** — `$...$`/`$$...$$` spans
  stay exactly as written. An embedding model's tokenizer treats
  `\lim_{x \to a}` as a sequence of subword tokens like any other text; it
  does not "understand" it as a limit any more than a human skimming
  would without training, but the *token sequence itself* is a real,
  useful, reproducible signal — two chunks both containing `\lim` and
  `\to` and `+\infty` will end up closer in embedding space than one that
  doesn't, and that is exactly the retrieval signal wanted. **No general-
  purpose text embedding model in 2026 has semantic understanding of
  LaTeX mathematics** — this is a genuine limitation to state honestly
  (§11 risks), not a solved problem.
- **Never generate an LLM paraphrase/summary of the math** — this is both
  explicitly forbidden by the task and would violate
  "do not destroy mathematical meaning": a paraphrase of
  `$\lim_{x \to -\infty} f(x)$` in words is itself a place to introduce an
  error a verbatim copy cannot.
- **The metadata template lines are plain French/section-title text** —
  no LaTeX is ever added to them, so they don't interact with or corrupt
  the math spans in `text`.

## 3. Embedding model recommendation

Researched directly (see Sources), not assumed. This project's own
criteria, checked against real candidates:

| Model | Params | Dim | Context | License | French | Notes |
|---|---|---|---|---|---|---|
| **BAAI/bge-m3** | ~568M | **1024** (fixed) | 8192 tokens | **MIT** | Strong (explicit multilingual training incl. French) | Dense + sparse + ColBERT-style multi-vector in one model; mature `sentence-transformers` support; MIRACL nDCG@10 67.8 (18 languages) |
| Qwen3-Embedding-0.6B | 0.6B | flexible/Matryoshka (up to 1024, truncatable) | long | Apache-2.0 | Yes (100+ languages; 8B sibling scores 69.8 on French in MTEB multilingual) | Lightest of the family, CPU-friendly; smaller model's own French MTEB score not separately published in what was found |
| zembed-1 (ZeroEntropy) | 4B | flexible (2560 down to 40) | long | Apache-2.0 (as of this research) | Multilingual, explicitly benchmarked on STEM/scientific text | Newest and least battle-tested of the four; heavier (4B) than BGE-M3 for comparable dimension |
| dangvantuan/french-document-embedding | — | — | — | — | French-specialized | Narrower language coverage; would not generalize to a future non-French subject/book, which this project's genericity requirement rules out as a default choice |

**Recommendation: BAAI/bge-m3.** Reasons, weighed against this project's
own priorities:

1. **French support**: explicitly multilingual-trained, benchmarked
   competitively against `multilingual-e5-large` on French-relevant tasks.
2. **Math/technical text**: no model here is math-native (§2), so this
   criterion reduces to "handles long, symbol-dense input without
   truncation" — BGE-M3's 8192-token context is the most generous of the
   four, comfortably covering even the corpus's 3022-character outlier
   many times over.
3. **Retrieval quality**: MIRACL/MTEB multilingual scores are
   competitive with or ahead of `multilingual-e5-large`, and it is a
   known, widely-benchmarked baseline (not a brand-new, less-verified
   entrant like zembed-1).
4. **Local inference**: 568M parameters is squarely CPU-feasible
   (confirmed this environment currently has no `torch`/
   `sentence-transformers` installed — see §11/§12, a real prerequisite,
   not assumed available); much lighter than zembed-1 (4B).
5. **No per-document API cost**: fully local, open weights, MIT license
   (the most permissive of the four — Qwen3/zembed are Apache-2.0, also
   fine, but MIT is one condition simpler).
6. **Vector dimension**: fixed 1024 — a very common, well-supported
   dimension across FAISS/Qdrant/pgvector/Chroma, simplest to reason
   about (vs. Matryoshka models where a truncation choice must ALSO be
   pinned and recorded).
7. **Ecosystem compatibility**: native, first-class `sentence-transformers`
   support (this project's most natural integration point), MIT license
   removes any ambiguity for a future production deployment.

**Documented alternative**: **Qwen3-Embedding-0.6B** if CPU/memory
constraints turn out to be tighter than expected once real hardware is
tested — smaller, still Apache-2.0, still multilingual, at some cost in
proven French/retrieval benchmarking specificity relative to BGE-M3.
**Not recommended for v1**: zembed-1 (newest, heaviest, least
community-adopted of the four, despite promising STEM benchmarks worth
revisiting later) and the French-specialist model (contradicts this
project's explicit "generic for future subjects" requirement).

## 4. Embedding metadata and identity

| Field | Required? | Why |
|---|---|---|
| `embedding_id` | Required | Deterministic (`emb-<chapter_id>-<chunk_id>-<model_name>-<model_revision>`), so the SAME chunk under a different model/revision gets a distinct id — never overwritten, never a counter. |
| `chunk_id` | Required | The join key back to `knowledge_chunks.json` — the entire reason provenance survives this phase. |
| `chapter_id` | Required | Namespaces embeddings per chapter, matching every prior phase's own output convention. |
| `content_hash` | Required | sha256 of the **exact embedding input string** (the §2 template output, not just `chunk["text"]`) — this is what makes "unchanged vs. changed" detection exact and cheap, without ever comparing floating-point vectors (§5/§8). |
| `embedding_model` + `model_revision` | Both required | A model *name* alone is not reproducible — weights can update under the same name. `revision` is an exact identifier (e.g. a HF commit SHA), recorded so the precise weights used are always knowable later. |
| `embedding_dimension` | Required | Needed to validate every vector's shape (§7) and to configure a future Vector DB's collection. |
| `normalization_strategy` | Required | `"l2"` or `"none"` — must be known to interpret the vectors correctly (cosine vs. dot-product assumptions differ) — see §7. |
| `created_at` | Required | When *this specific* embedding was computed — supports auditing/staleness questions independent of content_hash. |
| `pipeline_version` | Required | This design's own version tag (`embed-v1`) — distinct from `embedding_model`/`revision`, so a change to the *assembly template* (§2) itself is distinguishable from a change to the *model*. |

**Never rely on floating-point vector equality** to decide anything (§8) —
every "is this the same?" question in this design is answered by
`content_hash` + `(embedding_model, model_revision)`, never by comparing
vector components.

## 5. Idempotence and caching

Cache key: `(chunk_id, embedding_model, model_revision)`. On each run:

| Situation | Action |
|---|---|
| Unchanged chunk (same `content_hash`) + same model/revision | **Reuse** the existing record + vector row; no recomputation. |
| Changed chunk (embedding input's `content_hash` differs) | **Recompute** just that chunk's vector; new record replaces the old one (same `embedding_id` template, since chunk_id/model/revision are unchanged — the record's `content_hash`/`created_at` update). |
| Same chunk, different model or revision | **Compute a new, additional embedding** — a different `embedding_id`, coexisting with the old one (supports running/comparing multiple models side by side, and staged migration to a new model version). |
| Chunk deleted from `knowledge_chunks.json` | **Never silently delete.** Mark the record `status: "stale"` (§ manifest schema) and keep both the record and its vector row in place — mirrors this project's established "never silently discard, always mark for review" convention (Human Review, `review_status` fields throughout). A future cleanup step, not this one, decides whether to physically prune stale rows. |
| New chunk | **Compute** a new record + vector, appended. |

This directly supports **incremental processing**: a full chapter re-run
after only 3 chunks changed only calls the embedding model 3 times, not
102.

## 6. Output artifact

Following this project's own established convention exactly
(`data/output/<chapter_id>/<phase>/...`, used by every prior phase — NOT
the task prompt's illustrative `data/chapters/<book>/<chapter>/...`, which
doesn't match this repository):

```
data/output/<chapter_id>/embeddings/<model_id>/
    manifest.json     -- see embedding_manifest.schema.json
    vectors.npy        -- float32, shape (vector_count, embedding_dimension)
    records.json       -- list[EmbeddingRecord], see schema §EmbeddingRecord
```

`<model_id>` (e.g. `bge-m3`) namespaces embeddings per model, so
re-running with a different model never overwrites another model's
output — directly supporting "supporting multiple embedding model
versions" (§4).

- **`vectors.npy`**: a single 2D NumPy array. Row `i` is
  `records.json[i]`'s vector — **positional alignment is the entire
  contract between the two files**, which is exactly why it is validated,
  never assumed (§7).
- **`records.json`**: one `EmbeddingRecord` per vector row (schema
  above) — carries `chunk_id` (→ `knowledge_chunks.json`) and
  `filter_metadata.pdf_pages`/`section_id` (→ ultimately the source PDF
  page, via the chunk's own already-preserved provenance chain). The
  mapping `vector → chunk_id → source_item_ids → pdf_pages` can never be
  lost because every link in that chain already exists in an upstream
  artifact this phase only reads, never rewrites.
- **`manifest.json`**: one header record per (chapter, model) pair — see
  `embedding_manifest.schema.json`.

## 7. Vector validation

| Check | What it catches |
|---|---|
| Vector count == `records.json` length == `manifest.vector_count` | A silently truncated or duplicated run. |
| Vector dimension == `manifest.embedding_dimension` for every row | A model swap mid-run, or a corrupted `vectors.npy`. |
| NaN detection (`np.isnan(...).any()`) | A failed/garbage inference for some input. |
| Inf detection (`np.isinf(...).any()`) | Same class of failure, different symptom. |
| Empty/all-zero vector detection | An input that produced a degenerate embedding (e.g. an empty string slipped through). |
| Duplicate `embedding_id` | A cache-key collision or a re-run bug creating two rows for the same (chunk, model, revision). |
| Every `records[i].chunk_id` exists in `knowledge_chunks.json` | Orphan embeddings (§5's "deleted chunk" case must be `status: stale`, not silently left unlinked). |
| Every non-stale chunk in `knowledge_chunks.json` has a record | Missing embeddings (a chunk the pipeline never got to). |
| `model`/`revision` fields agree between every record and the manifest | A manifest/records desync (e.g. hand-edited files, a partially-applied migration). |
| `source_chunks_hash` in the manifest matches a fresh hash of the actual `knowledge_chunks.json` on disk | The embeddings on disk are stale relative to the CURRENT chunk file, even if no chunk_id changed identity (e.g. `knowledge_chunking.md`'s own algorithm_version bumped and regenerated text). |
| Recompute `content_hash` from each record's own `(chunk + template)` and compare | Detects the embedding input template (§2) itself changing without a version bump. |

**Should vectors be normalized?** **Yes — L2-normalize before storage**,
recorded via `normalization_strategy: "l2"`. Reasons: (1) cosine similarity
— the standard retrieval metric — reduces to a plain dot product on
L2-normalized vectors, which is what every mainstream vector index (FAISS
`IndexFlatIP`, Qdrant, pgvector) is optimized for; (2) normalizing once at
storage time is deterministic and cheap, removing any ambiguity later
about whether a consumer must renormalize before comparing.

## 8. Reproducibility

Four genuinely different things, not one:

1. **Reproducible pipeline configuration** — fully recorded and exactly
   reproducible: `pipeline_version`, the embedding-input template (§2,
   itself versioned), `normalization_strategy`, `embedding_model` +
   `model_revision`. Anyone with the same inputs and this same
   configuration can regenerate an equivalent run.
2. **Content identity** — `content_hash`, exact and deterministic (sha256
   of a plain string). Two runs either produce the identical hash or they
   don't; no ambiguity.
3. **Model identity** — `embedding_model` + `model_revision` is an exact,
   recorded identity, but this does NOT imply the model's own inference is
   bit-reproducible (below).
4. **Vector numerical equality** — **explicitly NOT required or assumed**.
   Floating-point results from a neural network can legitimately differ
   in the last few bits across CPU/GPU, BLAS library versions, or batch
   size, even with the identical model weights and input. This design
   never compares vectors for exact equality anywhere (§5, §7 both key on
   `content_hash`/ids, never on vector values). If a reproducibility CHECK
   is ever needed (not part of v1), it should compare **cosine similarity
   ≈ 1.0** (e.g. `> 0.999`) between an old and a freshly recomputed
   vector for the same `(content_hash, model, revision)` — never `==`.

## 9. Cost and performance

- **Local batch inference only** — `sentence-transformers`'s own
  `.encode(list_of_strings, batch_size=...)`, no network call, no
  per-chunk API cost, consistent with every prior phase's "zero LLM
  calls" constraint.
- **Batching**: process chunks in fixed-size batches (e.g. 16-32) rather
  than one `.encode()` call per chunk — this is a throughput concern only,
  never changes the recorded `content_hash`/identity per chunk.
- **Incremental processing**: §5's cache-key check happens BEFORE a chunk
  is even added to a batch — only genuinely new/changed chunks reach the
  model.
- **CPU/GPU compatibility**: `sentence-transformers` auto-detects an
  available GPU and otherwise runs on CPU; BGE-M3 at 568M parameters is a
  realistic CPU workload for a chapter-sized batch (102 chunks here).
- **Progress reporting**: log every N batches processed (matching this
  project's existing `logging`-based convention in every other phase's
  script, not a new UI).
- **Resumability**: because records are appended incrementally and keyed
  by `(chunk_id, model, revision)`, an interrupted run can simply be
  re-invoked — already-embedded chunks are skipped via the same cache
  check used for ordinary incremental runs (§5); no special "resume mode"
  is a separate code path.

## 10. Future Vector DB compatibility

This phase's output is deliberately the ENTIRE contract a future Vector DB
phase needs, and nothing more (no index built, no DB started, no
retrieval implemented):

- **Vector**: `vectors.npy` row, already L2-normalized, already the
  correct dimension.
- **Primary key**: `embedding_id` (globally stable) or `chunk_id` (stable
  per chapter+model).
- **Namespace**: `chapter_id` — maps naturally to a Vector DB
  collection-per-chapter or a `chapter_id` filter field, either is
  possible without changing this phase.
- **Filter/facet fields**: `filter_metadata` on every record already
  carries exactly the fields a retrieval UI would filter by (section,
  concepts, item type, content role, pages, uncertainty) — copied, never
  re-derived, from the chunk.
- **Model/version + dimension**: `manifest.json` — needed once, at Vector
  DB collection-creation time, not per vector.

## 11. Testing strategy

Designed around a **pure, injectable embedding function** (`Callable[[list[str]],
np.ndarray]`) so every test below runs without `torch`/
`sentence-transformers` installed (neither is currently present in this
environment — confirmed directly, a real, not hypothetical, constraint) —
tests use a small deterministic fake (e.g. a hash-based fixed-size vector
per string) to exercise the PIPELINE logic, never the real model's
numerical output:

- Embedding input construction (§2's template) — exact string assembly,
  field inclusion/exclusion, absent-field-omits-its-line behavior.
- Content hashing — same input → same hash; changed input → different
  hash; hash format matches `sha256:[0-9a-f]{64}`.
- Deterministic identity — `embedding_id` construction is a pure function
  of `(chapter_id, chunk_id, model, revision)`.
- Cache hit — same `(chunk_id, model, revision, content_hash)` on a
  second run reuses the existing record/row, does not call the (fake)
  embedding function again.
- Cache miss / changed chunk — a different `content_hash` for the same
  `chunk_id` triggers recomputation.
- Changed model — same chunk, different `model`/`revision` produces a
  second, additional record (§5), never replacing the first.
- Vector dimension validation — a fake embedding function returning the
  wrong shape is caught by validation, not silently stored.
- NaN/Inf validation — a fake function injecting `nan`/`inf` is caught.
- Missing chunk detection — a chunk present in `knowledge_chunks.json`
  with no corresponding record is flagged.
- Orphan embedding detection — a record whose `chunk_id` no longer exists
  in the current chunks file is flagged `stale`, not silently dropped or
  left inconsistent.
- Multiple chapters — running on two different chapters' chunk files
  never mixes their records/vectors (namespaced by `<chapter_id>/embeddings/<model_id>/`).
- Rerunning the pipeline (idempotence) — a full second run with zero
  chunk changes produces byte-identical `records.json` (aside from
  `created_at`) and calls the fake embedding function zero times.
- Stable chunk_id mapping — every record's `chunk_id` round-trips to a
  real chunk; `row_index` correctly indexes `vectors.npy`.

A **Chapter 1 regression test** additionally runs the same pipeline
against the real 102 chunks (with the fake embedding function — no real
model dependency in CI), asserting all of the above holds at realistic
scale, and that a grep-based check confirms no chapter-specific token
appears in the production module itself (the same discipline enforced in
every prior phase's own test suite).

## Final report

1. **Current chunk structure**: 102 chunks (101 statement + 1 correction),
   median 280 / max 3022 characters, **95% contain LaTeX, 46.9% of all
   characters are inside math delimiters** — a math-notation-dominant
   corpus, not prose with occasional formulas. Full metadata (topics,
   concepts, section/subsection, figure_refs, related_chunk_ids) already
   populated on every chunk.
2. **Recommended embedding input**: Option C — a deterministic template
   prepending `section_title`/`subsection_title`/`item_types`/`concepts`
   (all already on the chunk) before the verbatim, byte-for-byte
   unmodified `text`. No LaTeX simplification, no paraphrasing.
3. **Recommended model**: **BAAI/bge-m3** (MIT, 568M params, 1024-dim,
   8192-token context, mature multilingual/French benchmarks,
   `sentence-transformers`-native). Alternative: Qwen3-Embedding-0.6B
   (lighter, Apache-2.0) if CPU constraints demand it.
4. **Vector dimension**: **1024** (BGE-M3's native, fixed dimension).
5. **Normalization**: **L2-normalize at storage time** (`"l2"`), for
   cosine-similarity/dot-product compatibility with standard vector
   indexes.
6. **Identity/hash strategy**: `embedding_id` = deterministic function of
   `(chapter_id, chunk_id, model, revision)`; `content_hash` = sha256 of
   the exact embedding INPUT (template + text), never of `text` alone,
   never a vector comparison.
7. **Cache/incremental strategy**: key on `(chunk_id, model, revision)`;
   reuse on unchanged `content_hash`; recompute on change; new record
   (never overwrite) on model/revision change; `status: "stale"` (never
   silent deletion) for a chunk that disappears upstream.
8. **Output artifact**: `data/output/<chapter_id>/embeddings/<model_id>/{manifest.json,
   vectors.npy, records.json}` — matches this project's own established
   per-chapter, per-phase convention.
9. **Validation strategy**: 11 checks (§7) covering count/dimension/NaN/
   Inf/duplicates/orphans/missing/manifest-consistency/content-hash
   consistency — no check ever relies on float equality.
10. **Testing strategy**: pure-function design with an injectable fake
    embedding function so the full pipeline is testable without `torch`/
    `sentence-transformers` installed (confirmed absent from this
    environment today); 13 test categories + a Chapter 1 regression
    fixture, chapter-agnostic production code enforced by a grep test.
11. **Risks and limitations**: (a) no embedding model has genuine semantic
    understanding of LaTeX — retrieval quality on math-heavy queries rests
    on token-sequence similarity, not mathematical reasoning, and this is
    unlikely to change with any current general-purpose model; (b) the
    1500-character split threshold and merge/split rules are chunk-level
    concerns already fixed upstream — this phase inherits whatever
    granularity chunking produced and cannot correct it; (c) BGE-M3's own
    French-specific benchmark numbers were not as granularly available in
    this research as its aggregate multilingual scores — the
    recommendation rests on strong aggregate multilingual/French evidence,
